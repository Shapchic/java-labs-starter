## 1. Теоретические основы и контракты Object

### 1.1. Различие идентичности (`==`) и логического равенства (`equals`)
- **Идентичность (`==`)**: проверяет равенство ссылок в памяти (указывают ли две переменные на один и тот же адрес объекта в куче).
- **Логическое равенство (`equals`)**: определяет эквивалентность бизнес-состояния объектов в соответствии с их значимыми полями. Два разных объекта в памяти (`new SampleId("mnist", 1)` и `new SampleId("mnist", 1)`) имеют разную идентичность (`key1 != key2`), но логически эквивалентны (`key1.equals(key2) == true`).

### 1.2. Контракт методов `equals` и `hashCode`
Согласно спецификации языка Java:
1. **Рефлексивность**: для любого ненулевого `x`: `x.equals(x) == true`.
2. **Симметричность**: для любых `x` и `y`: `x.equals(y) == true` тогда и только тогда, когда `y.equals(x) == true`.
3. **Транзитивность**: если `x.equals(y) == true` и `y.equals(z) == true`, то `x.equals(z) == true`.
4. **Согласованность (консистентность)**: повторные вызовы `x.equals(y)` возвращают одинаковый результат, если поля объектов не менялись.
5. **Сравнение с `null`**: для любого ненулевого `x`: `x.equals(null) == false`.
6. **Связь с `hashCode`**:
   - Если два объекта равны по `equals`, их `hashCode` **обязаны** совпадать:
     $$a.\text{equals}(b) \implies a.\text{hashCode}() == b.\text{hashCode}()$$
   - Обратное неверно: совпадение `hashCode` **не гарантирует** равенства объектов (ситуация коллизии).

### 1.3. Принцип работы `HashMap` и почему ключи должны быть неизменяемыми
1. При вызове `map.put(key, value)` или `map.get(key)` вычисляется хеш-код ключа, по которому определяется номер корзины (bucket index) в массиве:
   $$\text{index} = \text{hash}(key) \pmod{\text{capacity}}$$
2. Внутри корзины поиск нужного узла производится вызовом метода `equals`.
3. Если ключ изменяем и его значимые поля изменились после добавления в таблицу:
   - Его `hashCode` меняется.
   - Последующий вызов `map.get(key)` ищет элемент в другой корзине и возвращает `null`.
   - Поиск по исходным значениям также завершается неудачей, так как метод `equals` вернет `false` при сравнении со смененными полями.
   - Объект оказывается «потерян» в памяти коллекции, нарушая целостность данных.

## 2. Архитектура решения (Вариант: Инженерия систем искусственного интеллекта)

### 2.1. Подготовительная часть (`Book`)
- **Класс `Book`**:
  - Неизменяемый класс (`final class`) с полями `isbn` и `title`.
  - Значимым полем для бизнес-идентификации книги является исключительно международный номер `isbn`.
  - Поля `equals` и `hashCode` переопределены согласованно с использованием только `isbn`. Книги с одинаковым `isbn`, но разными названиями (например, разные издания) логически равны и взаимозаменяемы в роли ключа `HashMap`.

### 2.2. Неизменяемый ключ `SampleId`
- **Класс `SampleId`**:
  - Представляет собой неизменяемый составной ключ наблюдения.
  - Состоит из двух значимых полей:
    - `dataset` (`String`) — наименование набора данных (например, `"mnist"`, `"cifar10"`);
    - `sampleNumber` (`int`) — порядковый номер образца в наборе.
  - Поля объявлены `private final`, защищены от модификации (отсутствуют сеттеры).
  - Конструктор гарантирует валидацию инвариантов: `dataset` не может быть `null` или пустым, а `sampleNumber` не может быть отрицательным.
  - Методы `equals` и `hashCode` строго согласованы и используют ровно один и тот же набор значимых полей (`dataset`, `sampleNumber`).

### 2.3. Доменная модель `DataSample` и статус `SampleStatus`
- **Перечисление `SampleStatus`**: жизненный цикл наблюдения (`RAW`, `PROCESSED`, `READY`, `REJECTED`).
- **Класс `DataSample`**:
  - Хранит идентификатор `SampleId id`, строковую метку `label`, текущий статус `SampleStatus status` и числовой вектор признаков `double[] features`.
  - Обеспечивает защитное копирование (`defensive copying`) массива признаков при создании и в методе доступа `getFeatures()`.

### 2.4. Реестр наблюдений `SampleRegistry`
- Реализован через композицию со стандартной коллекцией `HashMap<SampleId, DataSample>`.
- Поддерживает обязательные операции:
  - `put(SampleId id, DataSample sample)` / `addOrReplace(...)` — добавление или замена значения;
  - `get(SampleId id)` / `findById(SampleId id)` — получение значения (включая вариант с `Optional`);
  - `remove(SampleId id)` — удаление значения;
  - `containsKey(SampleId id)` / `contains(...)` — проверка наличия ключа;
  - `size()` — получение текущего количества записей;
  - `isEmpty()`, `clear()`, `getAll()` — вспомогательные методы управления коллекцией.

## 3. Обязательные эксперименты и их реализация в тестах

Все пять обязательных экспериментов покрыты модульными тестами в классах `SampleIdTest`, `SampleRegistryTest` и `BookTest`:

1. **Эксперимент 1 (Логическое равенство разных экземпляров):**
   - *Тест:* `SampleRegistryTest#shouldFindSameValueByDifferentInstancesOfLogicallyEqualKey`
   - *Результат:* Создаются два независимых объекта `key1` и `key2` с одинаковыми `dataset` и `sampleNumber` (`assertNotSame(key1, key2)`). Значение, добавленное по `key1`, безошибочно находится вызовом `registry.get(key2)`.

2. **Эксперимент 2 (Замена значения без увеличения размера):**
   - *Тест:* `SampleRegistryTest#shouldReplaceValueAndNotIncreaseSizeWhenAddingWithEqualKey`
   - *Результат:* Повторный вызов `put` по равному ключу заменяет старый образец данных на новый, возвращает предыдущее значение, при этом `registry.size()` остается равным 1.

3. **Эксперимент 3 (Разрешение намеренной коллизии `hashCode`):**
   - *Тест:* `SampleRegistryTest#shouldStoreDifferentValuesForUnequalKeysWithIdenticalHashCode`
   - *Результат:* Использованы строки `"FB"` и `"Ea"`, имеющие в JVM идентичный `hashCode = 2236`. Созданы два неравных ключа `SampleId("FB", 777)` и `SampleId("Ea", 777)`. Их хеш-коды строго равны, но `equals` возвращает `false`. При добавлении в `SampleRegistry` размер таблицы становится равным 2, и оба элемента корректно извлекаются без взаимной перезаписи.

4. **Эксперимент 4 (Сравнение с `null` и объектом другого типа):**
   - *Тест:* `SampleIdTest#shouldReturnFalseWhenComparedWithNullOrDifferentType`
   - *Результат:* Вызовы `id.equals(null)` и `id.equals("someString")` безопасно возвращают `false`, не вызывая исключений (`NullPointerException` или `ClassCastException`).

5. **Эксперимент 5 (Проблема изменяемого учебного ключа):**
   - *Тест:* `SampleRegistryTest#shouldDemonstrateProblemOfMutableKeyInHashMap`
   - *Класс:* `MutableSampleKey` (специальный тестовый ключ с изменяемыми полями и сеттерами).
   - *Результат:* Объект помещен в `HashMap`. Затем вызван `mutableKey.setDataset("cifar10")`. Хеш-код объекта изменился. Последующий `map.get(mutableKey)` возвращает `null`, `map.containsKey(mutableKey)` возвращает `false`, при этом элемент остается заблокированным в коллекции (`map.size() == 1`).

## 4. Дополнительная часть: `ChainedHashTable`

В рамках профиля «Инженерия систем искусственного интеллекта» реализована специализированная хеш-таблица с разрешением коллизий методом цепочек (отдельных списков) без использования обобщений (`generics`):

- **Класс `ChainedHashTable`**:
  - Ключи: `SampleId`.
  - Значения: `DataSample`.
  - Внутренняя структура: массив связных списков узлов `Node { SampleId key; DataSample value; Node next; }`.
  - Вычисление индекса корзины: сжатие 32-битного хеша с побитовым сдвигом `(h ^ (h >>> 16))` и операцией `Math.floorMod(hash, table.length)` для корректной работы с отрицательными значениями.
  - Динамическое масштабирование: при превышении коэффициента загрузки (`size >= threshold`, по умолчанию $0.75 \times \text{capacity}$) таблица автоматически удваивает размер массива корзин (`resize()`) и перехеширует все существующие узлы.
  - Покрыта полным набором тестов в `ChainedHashTableTest`: добавление, получение, замена, удаление из начала и середины цепочки, разрешение коллизий и расширение емкости с перехешированием 20+ элементов.
